## 2. วิธีที่เลือก (และทำไมครั้งก่อนไม่สำเร็จ)

ครั้งก่อน (`docs/FIREBASE_RULES_GUIDE.md`) เก็บ "บทบาท" ไว้ในฐานข้อมูล → พนักงานแก้ตัวเองเป็น Admin ได้
เพราะการบันทึกสต็อกต้องเขียนที่ราก (root) ของฐาน สิทธิ์เขียนจึงไหลลงทุกจุด

**แผนนี้เก็บบทบาทไว้ใน "บัตรผ่าน" (custom claims) ที่ Firebase ออกให้ ไม่อยู่ในฐานข้อมูล**
พนักงานแก้บัตรผ่านเองไม่ได้ → หลุมเดิมหายไป และ**ไม่ต้องย้ายข้อมูลเลย** (โครงสร้าง stock / transactions เหมือนเดิม)

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **A. Firebase Authentication (อีเมล+รหัส) + บทบาทในบัตรผ่าน (แนะนำ)** | มาตรฐาน · รีเซ็ตรหัสรายบัญชีได้ในหน้า Firebase · กันเดารหัสมีให้ในตัว · ฟรี | ต้องสร้างบัญชีครั้งแรกด้วยสคริปต์ |
| B. เซิร์ฟเวอร์ของเราตรวจรหัสเอง แล้วออกบัตรผ่าน | หน้า Login เหมือนเดิมทุกอย่าง | รหัสเก็บใน Vercel แก้ต้อง redeploy · ต้องดูแลการกันเดารหัสเอง |
| C. ย้ายข้อมูลไปโครงสร้างใหม่ตามแผนเดิม | — | งานมากกว่า เสี่ยงข้อมูลกว่า ไม่จำเป็นแล้ว |

**แนะนำ A**

## 3. สิ่งที่จะเปลี่ยน

| ส่วน | ตอนนี้ | หลังทำ |
|---|---|---|
| บัญชี | 10 บัญชีฝังในโค้ด | บัญชีเดิมทุกชื่อ (`user_nw`, `user_cm` …) เป็นบัญชี Firebase · ชื่อเดิม รหัสใหม่ไม่ซ้ำกัน |
| หน้า Login | เลือกชื่อ + รหัส ตรวจในเบราว์เซอร์ | หน้าตาเดิม ตรวจรหัสที่ Firebase |
| บทบาท / สาขา / คู่ค้า | อยู่ในเบราว์เซอร์ | อยู่ในบัตรผ่าน (ADMIN / USER+สาขา / PARTNER+คู่ค้า) |
| กฎฐานข้อมูล | ใครก็อ่าน/เขียนได้ | อ่าน/เขียนได้เฉพาะ ADMIN และ USER ที่ล็อกอิน · PARTNER และคนไม่ล็อกอิน = เข้าไม่ได้เลย · กฎตรวจรูปแบบข้อมูลเดิม (STEP1) คงไว้ |
| ซีโน่ (PARTNER) | — | ไม่แตะฐานข้อมูลตรง ๆ · หน้าซีโน่ขอข้อมูลจากเซิร์ฟเวอร์ (Vercel) ซึ่งตรวจบัตรผ่าน แล้วส่งกลับเฉพาะเอกสารของซีโน่ (ใช้โค้ด `utils/partnerPortal.ts` ที่ทำไว้แล้ว) |
| หน้าแรกก่อนล็อกอิน | เห็นสต็อกทุกสาขา | **ต้องล็อกอินก่อน** (รอคุณเท็นยืนยัน — ข้อ 6) |
| รหัส Admin พิเศษในหน้าตั้งค่า | ฝังในโค้ด | ใช้บทบาท ADMIN ในบัตรผ่านแทน |
| ส่ง Telegram | endpoint เปิดสาธารณะ | ตรวจบัตรผ่านก่อนส่ง (ปิดงานค้างใน `docs/TELEGRAM_TOKEN_MIGRATION.md`) |

**ที่ยังไม่ทำในรอบนี้ (คงเดิม):** พนักงานสาขาหนึ่งยังบันทึกแทนสาขาอื่นได้เหมือนวันนี้ (จำกัดรายสาขาเป็นงานถัดไป)
