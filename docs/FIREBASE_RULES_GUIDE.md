# คู่มือติดตั้ง Firebase Rules

## สรุปสั้น ๆ

ตอนนี้ฐานข้อมูลของเรา **เปิดให้ใครก็อ่านและเขียนได้** ใครที่รู้ URL ฐานข้อมูล
(ซึ่งเปิดอยู่ใน `index.html`) สามารถลบข้อมูลทั้งระบบได้จากนอกเว็บ

ไฟล์ `database.rules.STEP1-NO-AUTH.json` คือด่านแรกที่ปิดช่องโหว่นี้

---

## เปรียบเทียบให้เห็นภาพ

ระบบเรามีการเช็คสิทธิ์อยู่แล้ว 17 จุดในโค้ด เช่น
"ถ้าไม่ใช่ ADMIN ห้ามเห็นปุ่มลบ"

แต่การเช็คพวกนั้นอยู่ใน **เบราว์เซอร์ของผู้ใช้** — เหมือนติดป้าย "ห้ามเข้า"
ไว้หน้าประตู แต่ประตูไม่ได้ล็อก คนที่เดินอ้อมไปทางหลังก็เข้าได้อยู่ดี

Firebase Rules คือ **กุญแจล็อกจริง** ที่อยู่ฝั่งเซิร์ฟเวอร์ ผู้ใช้แก้ไม่ได้

---

## สองระดับ — เลือกตามความพร้อม

### ระดับ 1: ไฟล์ `database.rules.STEP1-NO-AUTH.json` (ใช้ได้ทันที)

**ทำอะไรให้:**
- กันสต็อกติดลบที่ระดับฐานข้อมูล (ต่อให้โค้ดพลาด ฐานข้อมูลก็ปฏิเสธ)
- กันข้อมูลผิดรูป เช่น `qty` เป็นตัวหนังสือ, `status` เป็นค่าที่ไม่มีในระบบ
- จำกัดความยาวข้อความ กันคนยัดข้อมูลขยะขนาดใหญ่
- เพิ่ม index ให้ค้นหาเร็วขึ้น

**ยังไม่ทำให้:**
- ❌ **ไม่ได้เพิ่มความปลอดภัยเลย** — ฐานข้อมูลยังเปิด public 100%
  ใครรู้ URL ก็ยังอ่าน เขียน และลบข้อมูลได้ทั้งหมด
- ❌ แบนเนอร์เตือนสีแดงใน Firebase Console **จะยังอยู่เหมือนเดิม**

**พูดให้ตรง:** กฎชุดนี้ = เพิ่มการตรวจความถูกต้องของข้อมูล ไม่ใช่การปิดช่องโหว่

### 💡 กฎเหล็กของ Realtime Database ที่ต้องจำ

> **สิทธิ์ `.write` สืบทอดลงล่าง และลูกยกเลิกไม่ได้**

ดังนั้นการเขียน `".write": true` ซ้ำใน `stock`, `transactions`, ฯลฯ
**ไม่มีผลอะไรเพิ่ม** เพราะ root เปิดไว้แล้ว — เคยใส่ไว้แล้วตัดออก
เพราะทำให้เข้าใจผิดว่ากันอะไรได้

สิ่งที่ได้ผลจริงในไฟล์นี้มีแค่ 2 อย่าง:
- `.validate` → ตรวจรูปแบบข้อมูล
- `.indexOn` → ทำให้ query เร็วขึ้นและหายเตือนใน log

**ทำไมยังเปิดอยู่:** เพราะระบบยังใช้รหัสผ่านในโค้ด (`1234` / `8888`)
ไม่ได้ใช้ Firebase Authentication ถ้าปิดตอนนี้ **เว็บจะใช้งานไม่ได้ทันที**

### ⚠️ ทำไม `.write` ที่ root ต้องเป็น `true`

ฟังก์ชัน `commitStockMutation` ใช้ `runTransaction` ที่ `ref('/')` เพื่อให้การแก้
`stock` และ `transactions` เกิดขึ้นพร้อมกันเป็นก้อนเดียว (atomic) — นี่คือหัวใจ
ที่ทำให้สต็อกไม่หายเมื่อมีคนบันทึกพร้อมกัน

Firebase กำหนดว่า **การเขียนที่ path ไหน ต้องมีสิทธิ์เขียนที่ path นั้น**
ถ้าตั้ง root เป็น `false` การบันทึกทุกรายการจะถูกปฏิเสธทันที (permission denied)

ความปลอดภัยจริงจึงมาจาก `.validate` ของแต่ละ path ด้านล่าง ซึ่ง**ยังคงทำงาน
เต็มที่แม้เขียนที่ root** (ทดสอบยืนยันแล้วด้วย Firebase emulator)

**หมายเหตุ:** ไฟล์ rules ไม่รองรับคอมเมนต์ — ห้ามใส่ `//` หรือ `"//"` ลงไป
เพราะ Firebase จะปฏิเสธทั้งไฟล์

### ระดับ 2: ปิดสนิท — **ยังทำไม่ได้ ต้อง migrate โครงสร้างก่อน**

ผมเคยเขียนไฟล์ `database.rules.STEP2-WITH-AUTH.json` ไว้ แต่**ลบทิ้งแล้ว**
เพราะทดสอบกับ emulator แล้วพบว่า **มีช่องโหว่จริง**: พนักงานทั่วไปสามารถ
ตั้งตัวเองเป็น ADMIN ได้

ถ้าเก็บไฟล์นั้นไว้ อาจมีคนหยิบไปใช้แล้วเข้าใจผิดว่าปลอดภัย

#### ทำไมถึงเป็นแบบนั้น (สาเหตุที่แท้จริง)

Realtime Database มีกฎเหล็กข้อหนึ่ง:

> **สิทธิ์ `.write` ที่ให้ไว้ชั้นบน จะไหลลงลูกทั้งหมด และลูกปฏิเสธไม่ได้**

`commitStockMutation` ทำ `runTransaction` ที่ `/` (root) เพราะต้องแก้ `stock`
กับ `transactions` พร้อมกันเป็นก้อนเดียว แต่ Firebase บังคับว่า transaction
**ต้องคืนค่าทั้งก้อนของ node ที่ทำ**

ผลลัพธ์เป็นลูกโซ่:

```
ทำ transaction ที่ root
   ↓
rules ต้องเปิด .write ที่ root
   ↓
สิทธิ์ไหลลงทุก node รวมถึง users/
   ↓
พนักงานเขียน users/<uid>/role = 'ADMIN' ได้
```

**ทดสอบยืนยันแล้ว** — พนักงานเลื่อนตัวเองเป็นแอดมินได้จริง

#### ทางแก้: ต้อง migrate ก่อน (วางแผนแยกต่างหาก)

ย้าย `stock` กับ `transactions` ไปอยู่ใต้ node เดียวกัน:

```
ก่อน                     หลัง
/stock                   /inventory/stock
/transactions            /inventory/transactions
/config                  /config      (อยู่ที่เดิม)
/branches                /branches    (อยู่ที่เดิม)
```

แล้วเปลี่ยน `runTransaction(ref(db, '/'))` เป็น `runTransaction(ref(db, 'inventory'))`

หลังจากนั้น rules จะเขียนแบบนี้ได้ และปลอดภัยจริง:

```json
{
  "rules": {
    ".read": "auth != null",
    ".write": false,
    "inventory": { ".write": "auth != null" },
    "users": {
      "$uid": {
        ".write": "root.child('users').child(auth.uid).child('role').val() === 'ADMIN'"
      }
    }
  }
}
```

**งานที่ต้องทำ:** แก้จุดอ่าน/เขียน 13 จุดใน `services/firebase.ts`
+ เขียนสคริปต์ย้ายข้อมูลเดิม + ทดสอบ + เตรียม rollback

ประเมิน ~1-2 วัน ควรทำพร้อมกับตอนติดตั้ง Firebase Auth

## วิธีติดตั้ง (ทำครั้งเดียว ~5 นาที)

1. เปิด https://console.firebase.google.com
2. เลือกโปรเจกต์ **pallet-management-system-310ed**
3. เมนูซ้าย → **Realtime Database**
4. แท็บ **Rules** (อยู่ด้านบน)
5. **คัดลอกกฎเดิมเก็บไว้ก่อน** — วางในไฟล์ text ไว้ที่เครื่อง เผื่อต้องย้อนกลับ
6. ลบของเดิมทิ้ง แล้ววางเนื้อหาจาก `database.rules.STEP1-NO-AUTH.json` ลงไป
7. กด **Publish**

## ทดสอบหลังติดตั้ง (สำคัญ — ห้ามข้าม)

ทำตามนี้ทีละข้อ ถ้าข้อไหนไม่ผ่าน ให้ย้อนกลับทันที (ดูหัวข้อถัดไป)

| # | ทดสอบอะไร | ผลที่ควรได้ |
|---|---|---|
| 1 | เปิดเว็บ ดูหน้าแรก | เห็นข้อมูลสต็อกปกติ |
| 2 | บันทึกรายการรับเข้า 1 รายการ | บันทึกได้ ยอดเพิ่มถูกต้อง |
| 3 | บันทึกรายการจ่ายออก 1 รายการ | บันทึกได้ ยอดลดถูกต้อง |
| 4 | ยืนยันรับของที่ค้างอยู่ | สถานะเปลี่ยนเป็นเสร็จสิ้น |
| 5 | ยกเลิกเอกสาร 1 ใบ | ยอดคืนกลับถูกต้อง |
| 6 | ลองจ่ายออกเกินจำนวนที่มี | **ต้องขึ้นเตือน "สต็อกไม่เพียงพอ"** |
| 7 | บันทึกงานซ่อมบำรุง | ยอดย้ายเข้าคลังซากถูกต้อง |

## วิธีย้อนกลับ (Rollback)

ถ้าเว็บใช้งานไม่ได้หลังติดตั้ง:

1. กลับไปที่ Firebase Console → Realtime Database → Rules
2. วางกฎเดิมที่คัดลอกเก็บไว้ในขั้นตอนที่ 5 กลับลงไป
3. กด **Publish**

ระบบจะกลับมาใช้งานได้ทันที (ภายใน ~10 วินาที)

**ถ้าไม่ได้เก็บกฎเดิมไว้** ให้ใช้กฎเปิดโล่งชั่วคราวนี้เพื่อกู้ระบบก่อน
แล้วค่อยแก้ทีหลัง:

```json
{
  "rules": {
    ".read": true,
    ".write": true
  }
}
```

⚠️ กฎข้างบนนี้ **ไม่ปลอดภัย** ใช้เพื่อกู้ระบบชั่วคราวเท่านั้น

## วิธีทดสอบ Rules ก่อน Publish (ทำในเครื่องได้ ไม่กระทบข้อมูลจริง)

กฎชุดนี้ **ผ่านการทดสอบด้วย Firebase Emulator แล้ว 15/15 ข้อ** ครอบคลุมทั้ง
ข้อมูลถูกต้องต้องเขียนได้ และข้อมูลผิดต้องถูกปฏิเสธ

ถ้าแก้กฎเพิ่มในอนาคต ให้ทดสอบซ้ำแบบนี้:

```bash
firebase emulators:start --only database --project demo-test
```

แล้วเขียนสคริปต์ทดสอบด้วย **Firebase client SDK** ยิงไปที่ emulator

### ⚠️ กับดัก 2 ข้อที่เสียเวลามาแล้ว

**1. REST API ข้าม rules ทั้งหมด**

การทดสอบด้วย `curl .../stock.json` จะ**ผ่านทุกกรณี**แม้ข้อมูลผิด
เพราะ REST endpoint ของ emulator ถือว่าเป็น admin

→ ต้องทดสอบผ่าน **client SDK** (`firebase/database`) เท่านั้น
จึงจะเห็นผลตรงกับที่เว็บจริงเจอ

**2. namespace ต้องตรงกัน**

emulator โหลด rules ให้ namespace ชื่อ `<project-id>-default-rtdb`
ถ้าเชื่อมต่อไปที่ `<project-id>` เฉย ๆ จะได้ namespace อื่นที่**เปิดโล่ง**
ทำให้เข้าใจผิดว่ากฎไม่ทำงาน

→ ตรวจชื่อ namespace ที่ถูกต้องได้จาก `database-debug.log`

## ข้อควรระวัง

**`.validate` ทำงานกับข้อมูลใหม่เท่านั้น** — ข้อมูลเดิมที่ผิดรูปอยู่แล้ว
จะไม่ถูกลบหรือแก้ แต่ครั้งต่อไปที่มีการเขียนทับจุดนั้น กฎจะเริ่มบังคับใช้

ถ้าพบว่าบันทึกไม่ผ่านเพราะข้อมูลเดิมผิดรูป ให้ดูข้อความ error
ใน DevTools Console (กด F12) จะบอกว่าติดกฎข้อไหน
